# M1：权威匹配到房间闭环设计

## 目标与边界

本阶段交付两名已认证玩家从匹配入队到获得同一房间 ID 的完整闭环。服务端创建房间并向双方推送对手资料；客户端显示匹配已成功的暂存状态。

本阶段不实现战斗 tick、位置同步、伤害结算、ELO 结算、断线重连、数据库迁移或匹配取消。它们依赖可靠的房间创建，留待后续阶段。

## 所有权与组件

`GameServer` 主 `EventLoop` 独占 `MatchQueue`、`RoomService` 与匹配定时器。它们只在该 loop 的回调中读写，因此这些状态之间不引入额外锁。

`Room` 只保存不可变的房间 ID 和两名玩家的用户 ID。`RoomService` 负责生成单调递增的非零房间 ID、保存房间，以及按 ID 查询房间。它不处理网络连接和战斗规则。

`SessionService` 保持连接到玩家会话的映射。房间创建后，服务端把两个会话的 `roomId_` 设为新房间 ID；连接断开时先用仍有效的会话取得用户 ID，取消排队，再移除会话。

## 匹配流程

服务端初始化完成后，用 `EventLoop::runEvery()` 每 100ms 执行一次匹配 tick。一次 tick 重复调用 `MatchQueue::tryMatch(MatchClock::now())`，直到没有可匹配的玩家。

每取得一对玩家，服务端按以下顺序完成状态转换：

1. 确认两名用户仍有有效会话，且其 `roomId_` 均为零。
2. 由 `RoomService` 创建房间。
3. 通过 `SessionService` 将双方标记为在该房间中。
4. 分别向双方发送包含同一 `roomId_`、对方用户资料的匹配成功通知。

以上状态变更和通知安排均在同一 EventLoop 回调内完成；连接断开回调不会在中间交错执行。消息发送仍采用既有 TCP 长度前缀帧，客户端必须按消息类型分发和严格解码。

若步骤 1 的任一玩家已不存在或已经在房间中，本阶段记录错误并不创建房间。该情况不应由正常单线程流程产生；它是状态不变量被破坏时的防御性保护。

## 协议与客户端状态

在 `GameProtocol` 中新增 `MSG_MATCH_FOUND_NTF`。既有 `MatchFoundNotification` 作为其 payload，不改动字段布局。

LobbyScene 点击匹配后发送空 payload 的 `MatchJoinRequest`，并保持现有的 `REQUESTING...` 展示。收到 `MatchJoinResponse`：接受时进入等待状态，拒绝时恢复可点击并展示服务器错误信息。收到 `MatchFoundNotification`：验证 payload 后显示匹配成功和对手资料，作为进入 BattleScene 前的临时终态。

客户端不自行生成房间 ID，也不推测是否匹配成功；房间状态完全以服务端通知为准。

## 测试与验收

测试源码必须进入版本控制，且构建产物不得提交。先恢复并提交 `MatchQueueTest` 和 `MatchMessageTest`，再新增：

- `RoomServiceTest`：创建房间返回非零且递增的 ID；房间保存正确的两名玩家；查询不存在房间失败。
- GameServer 匹配集成测试：两名已认证、不同连接的玩家入队后，下一次匹配 tick 创建同一房间；双方会话的 `roomId_` 相同；双方收到对手资料正确的 `MSG_MATCH_FOUND_NTF`；队列中不再包含两人。
- LobbyScene 测试：点击匹配发送请求；接受、拒绝和匹配成功三种服务器结果产生确定的 UI 状态。

验收以两名独立客户端的端到端手工测试补充自动测试：双方点击匹配后，最多一个 100ms tick 周期进入同一房间并各自显示对手资料。

## 提交边界

M0 先单独提交现有 LobbyScene 改动、服务器断线时的重复会话清理修复，以及已验证的测试基础设施。M1 再按协议与领域模型、服务端匹配闭环、客户端状态处理三个逻辑单元分别测试并提交。
